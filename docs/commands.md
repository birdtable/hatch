# Command reference

Every command, its flags and its exit codes. Run a command with no flag, or a wrong one, to see its usage.

- `hatch budget`: the load-aware tier budget. A tier over its time is judged strictly on a quiet machine, and is noted, not failed, when the load is above `--limit` at the sample `--loaded-when` names: `before` the tier, at its `end`, `either` (the end sample counts alone when none was taken before) or `before-and-end` (both, so a tier with no sample before it is never excused). `--load-before` is a load the caller sampled before its first unit of work on the machine (`hatch budget --load`): a sample taken between two tiers of one run holds the earlier tier's load and tells nothing about another job. The end sample always holds the judged tier's own load, so `end` and `either` excuse a tier by its own work and are for a caller whose tier does not load the machine (it waits on the network or on another host); to tell another job's load from the tier's own, pass `before` or `before-and-end` with a sample from before the run. The load line names the CPU count the load was read on; hatch has no per-CPU limit, so the caller works `--limit` out. hatch holds no project policy: the caller passes the budgets file (`--budgets`), the expression that reads one row of it (`--row`, with the named groups `id` and `limit`, the limit in seconds), the row id (`--prefix` and `--tier`), the load average to read (`--window`: 1, 5 or 15 minutes), the load threshold (`--limit`), the words of the load lines (`--noun`, `--excused`, both required with `--limit`) and the advice on a failure (`--advice`). With no `--window` no load is read, with no `--limit` the load excuses nothing, and with no `--advice` a failure adds none. Where the system has no load average, the budget is judged strictly. `hatch budget -h` says what each unset flag means.
- `hatch tests --timeout <duration> --red-when <rule> --green-word <word> --red-word <word> [go test arguments]`: the caller says which counts make a run red and which words the verdict line ends on, and none is assumed. `--red-when` names from `failed`, `none-ran` (no test passed or skipped), `all-skipped` and `any-skipped` (one or more tests skipped, the first 10 named in the red line), joined with commas; a name left out never makes a run red. `--green-word` and `--red-word` are required, not blank, and differ. A flag left out, a blank or unknown rule name, or a repeated one is refused with exit 2. The run goes through go-proc's `proc.Run`: `--timeout` is required (a run with none is refused), and a run that reaches it is killed, tree and all, and is red. The test stream is held until the run ends, printed on a red and dropped on a green, but for one line for each skipped test of a green run, `hatch tests: skipped <package>.<Test>: <reason>` (the reason its `t.Skip` gave, or "no reason given"), printed above the verdict line, which stays the last; a run with no skips prints none, and the exit codes and `--red-when` are as before. `--stream` is opt-in: it also prints one line for each package, `pass`, `fail` or `skip` and its import path, as that package's event arrives, before the verdict line; the counts, the verdict, the exit code and what a red run prints are as without it. `-timeout` with one dash is go test's own and passes through.
- `hatch tests packages [exclude...]`: prints the import paths of `go list ./...`, one a line, without the paths named. An exclude is an exact import path, or one ending in `/...`, which drops that path and everything under it. The list is the caller's: no path is dropped by default. It exits 1 when nothing is left, 2 on a blank or flag-like exclude or a failed `go list`, and 3 when go is not on PATH. It does what `go list ./... | grep -v` does, in one command that runs the same on Windows.
- `hatch names --list <file> [--outside-tree] [--exceptions <file>] [--dir <folder>] [--tree] [--branch] [--base <rev>] [--addresses <regexp>] [--stdin]`: checks a hashed list of forbidden names. A list line is the SHA-256 of a name, folded to lower case, then an optional letter count and a what; `hatch names hash [--letters]` makes the lines from a name on stdin, never from an argument. At least one surface is required: `--tree` (each tracked file and its path), `--branch`, `--base` (each commit past the revision: message, added lines, added paths), `--addresses` (each commit's author and committer address must match the pattern whole) and `--stdin` (text such as a pull request's title and body). A name is found as a run of 1 to 4 words, spaced or run together, split where case turns; a row with a letter count is also found glued inside a longer word, and hyphen-joined words as written. `--exceptions` is a file of stanzas (`file`, one of `pattern` or `what`, and `why`); an exception nothing used is reported. `--outside-tree` refuses a list that lies in the work tree; the list's place is the caller's. The list and the exceptions file are read through go-files' `trust.ReadOwned` with a limit of 1 MiB: each must be a regular file, reached through no link, that the running account (or root, on Windows the system account) owns and no other account can write; a refusal exits 2 and names the flag and a reason, never a path. A finding prints `<name>`, the file and the line, and never the name. Before each scan a made-up name is planted on every surface and the run fails if the scan misses it. It exits 0 clean, 1 on a finding, 2 on a usage or run error or anything it cannot read or prove, and 3 when git is not on PATH.
- `hatch runs --rules <file> [--root <dir>]`: finds, per package of a Go module, each external program it starts and judges that against a rules file. It reads the tracked non-test Go files of the module at `--root` and resolves the program named to `exec.Command`, `exec.CommandContext` and `exec.LookPath` with `go/types` from the module's own source, so a constant declared in another package of the module counts. `--rules` is required and has no default. A row is `<program> <package>...`, the packages that may start that program; the row `unseen <package>...` names the packages that may start a program chosen where the check cannot see (a parameter, a field, a package variable, another package's function). Red, one line each: a program started from a package not on its row, a program with no row, an unseen site in a package not on the `unseen` row (file and line), a row or a package on a row that nothing used, and a file that does not parse. Green prints one line with the counts. `hatch runs list [--root <dir>]` prints `<package> <program>` lines and the unseen sites and judges nothing. What it does not see: a dot-imported `os/exec`, an `exec.Cmd` with `Path` set, `os.StartProcess` and `syscall.Exec`; the lint rows cover those (depguard on `os/exec`, forbidigo on the other calls). It exits 0 green, 1 on a finding, 2 on a usage or run error or anything it cannot read, and 3 when git is not on PATH.
- `hatch age --days <n> --modfile <go.mod path> [--modfile ...] [--exceptions <file>] [--timeout <duration>]`: refuses a Go module version younger than the caller's window, the days since its release read from the go command's own answer to `go list -m -json -modfile=<file> all` (the module proxy or the cache, so hatch holds no registry client), for each modfile the caller names, `go.mod` and each `tools/*.mod`. A line on stdout for each module refused: younger than `--days` (naming its release time and the UTC day it is allowed from), a pseudo-version (its time is its commit's own and can be any date), or with no release time (a module replaced by a folder), each by `<module>@<version>` of its require line, which is the key an exception takes; a module replaced by another module is judged by the replacement. `--days` and `--modfile` are required and there is no default window. `--exceptions` is a file of one `<module>@<version> <reason>` line each (blank and `#` lines skipped; a line with no reason, a key twice or a file that cannot be read is exit 2): an excepted module is allowed and printed with its reason, and an exception that matches no module that is refused is printed and does not fail the run. Exit 0 green, 1 a module refused, 2 a usage error or a go list that failed (a cold cache with no network is never green), 3 go not found. The main module is not judged; Go modules only, so pnpm packages and tools that are not Go modules are not checked.
- `hatch tag --remote <name> --branch <name> [--dir <folder>] <version>`, `hatch tag --remote <name> --snapshot [--dir <folder>]` and `hatch tag --remote <name> --tagged [--on <branch>] [--dir <folder>] <version>`: the release tag guard. It holds a tree to what a release built from it must be, at three moments. Every moment refuses a tree that is not clean. Before the tag: HEAD is `--branch`, the remote's branch is the same commit (not behind, ahead or apart), and `<version>` is a tag neither here nor on the remote. `--snapshot` (the recipe's dry release) runs at any sha: on a branch the remote holds, the branch is the remote's. `--tagged` (the publish): HEAD is the annotated tag `<version>`, and the remote's tag is the same commit, which is an ancestor of the remote's default branch (`refs/remotes/<remote>/HEAD`, or `git ls-remote --symref`) or of the branch `--on` names, so a tag on a side branch is refused by name; a lightweight tag is refused. `--prefix <folder>` (any moment but `--snapshot`) makes the tag `<folder>/<version>` for a module in a folder: one or more slash-separated names of lower case, digits, `-`, `.` and `_`, with no `..`. `<version>` is a release tag, `v` and a semantic version with a pre-release allowed, as the caller's changelog tool prints it (hatch reads no changelog), and is refused before git is asked when it is not. The remote and the branch have no default. It asks the remote with `git ls-remote` and changes no ref, with the caller's own environment (its HOME, so its git configuration and sign-in) and no prompt, and a remote that is asked and cannot be read is a refusal; `--snapshot` on a detached HEAD asks none, as there is no branch to compare, so it passes there whatever the remote is; a ref whose name only ends as the tag's does not answer for it. A refusal names its reason on stderr and exits 1, a pass prints one line, exit 2 is a usage error and 3 is no git.
- `hatch writes [--root <dir>] [--max-entries <n>] [--max-bytes <n>] [--timeout <duration>] -- <command> [args]`: holds a command to writing nothing under a root. It lists the tree with go-files' `treesum` before the command and after it (every file by the hash of its content, every link by its target and never followed, every folder, the files git ignores and a folder named `.git` among them) and prints each path that was added, changed or removed as `added <path>`, `changed <path>` or `removed <path>`, one per line, sorted by path, on stdout; it is green only when there are none. A mode, a time and an owner are not listed, so a file written again as it was is no write. The root is `--root`, or the top of the git checkout the working folder is in; the caps are `--max-entries` (default 200000) and `--max-bytes` (default 1 GiB), and `--timeout` (default 30 minutes) ends the command and its tree. A command that fails ends the run with its own exit code, and the list of what it wrote is printed beside it; a command that is ended or killed by a signal is exit 1. What treesum refuses (a device, a FIFO, a socket, a file with a second name, a link that leads out of the tree or loops, a name that is not UTF-8 text, a tree over a cap) is exit 1 naming the path, before the command, which is then not run, or after it; nothing is skipped. There is no way yet to leave a folder out: a command that touches `.git` (git status refreshes its index) or a tree with `node_modules` hard links is red, so the caller takes a `--root` below them. An exclude has to be made inside the walk, and is asked of go-files. Exit 2 is a usage error or a command that cannot be started, and 3 is no git when no `--root` is given.
- `hatch secrets [--range <base>..<head> | --staged] [--gitleaks <path>] [--config <file>] [--dir <folder>] [--timeout <duration>]`: runs the caller's gitleaks over the whole history of the repository (`gitleaks git --redact`) and is green only when gitleaks ran, scanned at least one commit and found nothing; green prints the count. `--gitleaks` names the caller's pinned binary, a path or a name looked up on PATH, and defaults to `gitleaks` on PATH: hatch does not fetch it and has no other default. `--config` is passed to gitleaks. Red, with its reason on stderr: git reports no commit; the repository's config sets `format.pretty` (gitleaks v8.30.1 then reads no commit and exits 0); gitleaks is not found or does not start; gitleaks exits with anything but 0; gitleaks logs an error; its output does not hold exactly one count of commits scanned; the count is 0. `--range <base>..<head>` scans only the commits of that range (`gitleaks git --log-opts`) and is red unless gitleaks's count of commits scanned equals the commits git's `log --text -p --diff-merges=first-parent <range>` shows adding a line, which is the set gitleaks v8.30.1 counts (an empty commit, and a commit that only deletes, renames or changes the mode of a file or adds a binary or an empty file are in neither count; a merge is in it by its diff against its first parent; a gitleaks bump can move the set, and the real-gitleaks test shows it); a range that holds none is red by name. `--staged` scans the staged change as a range of one: `git write-tree` and `git commit-tree <tree> -p HEAD` (no parent before the first commit) make a temporary commit object of the index, which gitleaks reads as it reads a range, with the same `--text`, attributes and merge options and the count held to 1, so a rule keyed on a path and a binary file's content are both read, and it needs no commit of its own; no ref or work tree moves, and the unreferenced objects are left for `git gc`. The index it reads is the one the caller's `GIT_INDEX_FILE` names, made absolute (git hands a pre-commit hook of `git commit -a` or `git commit <path>` `.git/index.lock` or `.git/next-index-<pid>.lock`, not `.git/index`), and only `git write-tree` gets that variable. `write-tree` takes that index file's lock and writes its cache tree back, so "no index moves" holds for its entries and not for the file's bytes, and a run red because that lock is held says so by name. gitleaks's own `git log` runs with `--no-ext-diff --no-textconv`, so a repository's own diff driver cannot change the text it reads. A staged change that adds no text (a mode change, a rename, a delete) is red as `nothing is staged`, an unmerged index is red by name, and the gitleaks config's path allowlist applies as in a range. The two flags are not given together. Every git call, gitleaks's own included, reads its attributes from the empty tree (`GIT_ATTR_SOURCE`), so a `.gitattributes` that marks a file `-diff` or `binary` hides nothing from any mode; that needs git 2.42 or later, and an older git is red by name, never run without it. A file git judges binary (one NUL byte is enough) is read as text in every mode (`--text`), so a secret in it is found, and a clean image is green; the gitleaks config's own path allowlist still applies, the default's image paths (`.png`, `.jpg` and others) included, because that allowlist is the caller's policy and hatch does not override it: a caller who wants images read passes `--config` a config without them. Every mode that reads commits puts each merge's own diff, against its first parent (`--diff-merges=first-parent`), before gitleaks, so a secret written only in a merge's resolution is read; that diff holds what the side branch brought too, which the side's own commits showed already. Git runs through go-proc with `gitenv`. What a finding holds is printed only as gitleaks prints it with `--redact`. It exits 0 green, 1 red, 2 on a usage error, and 3 when git is not on PATH.

## Notes

`hatch tests` does not run the `gotestsum` command with a post-run script: the command would be a second program to install, and it starts `go test` itself, outside `proc.Run`, which is what gives `--timeout` its tree kill. Only the `testjson` package is linked, and the run stays through `proc.Run`. `testjson` carries no API promise: its changelog is read at each bump of `gotest.tools/gotestsum`. It reads a line only up to the limit of `testjson`'s own scanner; `go test -json` cuts its output into events of about 1 KiB, so a real stream holds none longer, and a longer line ends the run with exit 2 and the scanner's error, never with a wrong count. A plain `FAIL` line in the stream is passed over by `testjson` with a `WARN` line on stderr, and no count changes.

## Systems

Linux, macOS and Windows, on amd64 and arm64.

`hatch budget --cpu --cpu-row <expr> ... -- <command>` judges a tier by CPU time instead of wall time: hatch runs the command in a tree of its own and holds the user plus system time of that tree to the tier's CPU row, which is the same on a quiet machine and a loaded one. The CPU row alone decides over or under: a tier over its wall limit with its CPU under passes, and the output names its wall time and the load. Wall time is a hang guard only: a command still running at ten times the tier's wall limit is killed and fails as hung. A tier with no CPU row is refused by name. A tree that cannot be read whole fails by name and never passes: on Unix a descendant that outlived the command, which its parent did not wait for, and on Windows a tier that cannot be put in a job object.

On Windows there is no load average, so `hatch budget` reads none: the load is reported as unknown, excuses nothing, and a tier over its time is judged strictly, as it is with no `--window`.
